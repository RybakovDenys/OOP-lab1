# Лабораторна робота 1 — Варіант 7 «Лицар»

Консольний Java-додаток, що моделює ієрархію амуніції лицаря, екіпірує
лицаря, рахує вартість амуніції, сортує її за вагою і шукає елементи
амуніції в заданому діапазоні ціни.

## Умови варіанту

> Лицар. Визначити ієрархію амуніції лицаря. Екіпірувати лицаря.
> Порахувати вартість. Провести сортування амуніції на основі ваги.
> Знайти елементи амуніції, що відповідають заданому діапазону
> параметрів ціни.

## Структура пакетів

```
ua.lab.knight
├── Main.java              // точка входу, консольна демонстрація
├── Knight.java             // клас лицаря: екіпірування, вартість, сортування, пошук
├── EquipmentSlot.java       // enum слотів екіпіровки
├── equipment
│   ├── Equipment.java       // абстрактний базовий клас амуніції
│   ├── Armor.java           // абстрактний клас броні (успадковує Equipment)
│   ├── Helmet.java          // шолом (успадковує Armor)
│   ├── Chestplate.java      // кіраса (успадковує Armor)
│   ├── Leggings.java        // набедренники (успадковує Armor)
│   ├── Gauntlets.java       // рукавиці (успадковує Armor)
│   ├── Boots.java           // чоботи (успадковує Armor)
│   ├── Weapon.java          // зброя (успадковує Equipment напряму)
│   ├── WeaponType.java       // enum типів зброї
│   └── Shield.java          // щит (успадковує Equipment напряму)
└── util
    └── EquipmentLoader.java // завантаження параметрів ініціалізації з файлу
```

### Чому саме така ієрархія

`Equipment` — спільний абстрактний предок з властивостями `name`, `weight`,
`price`, `material`, спільними для будь-якого елементу амуніції.

`Armor` успадковує `Equipment` і додає `defenseBonus` — це має сенс, бо всі
предмети броні (шолом, кіраса, набедренники, рукавиці, чоботи) справді є
"різновидом" броні (is-a) і різняться лише слотом екіпіровки.

`Weapon` і `Shield` успадковують `Equipment` напряму, а не `Armor`, бо зброя
й щит не є бронею — успадкування застосовано лише там, де воно логічно
виправдане, як і вимагається умовою лабораторної роботи.

Поліморфізм демонструється через абстрактні методи `getCategory()`,
`getSlot()` та `describeCombatValue()`, які по-різному реалізовані в
кожному класі.

## Ініціалізаційні дані

Параметри амуніції зберігаються у файлі
`src/main/resources/equipment.txt` (текстовий формат з роздільником `;`),
який зчитується класом `EquipmentLoader` при старті програми. Це дозволяє
змінювати набір амуніції лицаря без перекомпіляції коду.

## Збірка та запуск

Проєкт зібрано на Maven (Java 17+, JUnit 5, Mockito).

```bash
# Зібрати проєкт і прогнати тести
mvn clean verify

# Запустити консольний застосунок
mvn compile exec:java -Dexec.mainClass=ua.lab.knight.Main

# або зібрати jar і запустити
mvn package
java -jar target/knight-equipment.jar
```

Під час виконання застосунок:

1. Завантажує амуніцію з файлу `equipment.txt`.
2. Екіпірує нею лицаря (по одному предмету на кожен слот).
3. Виводить весь спорядок і його сумарну вартість та вагу.
4. Виводить амуніцію, відсортовану за вагою (зростання).
5. Пропонує ввести мінімальну і максимальну ціну та виводить елементи
   амуніції, ціна яких потрапляє в заданий діапазон.

## Тестування

Усі класи покриті Unit-тестами (JUnit 5):

- `equipment/*Test.java` — валідація параметрів конструктора, коректність
  `getCategory()`/`getSlot()`/`describeCombatValue()`, `equals`/`hashCode`,
  поліморфна робота зі списком `Equipment`.
- `KnightTest.java` — екіпірування/заміна предметів у слотах, розрахунок
  вартості та ваги, сортування за вагою (зростання/спадання), пошук за
  діапазоном ціни (включно з межовими та некоректними випадками).
- `util/EquipmentLoaderTest.java` — парсинг файлу ініціалізації, обробка
  коментарів і порожніх рядків, помилки при невідомій категорії чи
  пошкодженому рядку.

```bash
mvn test
```

## Кодстайл

Код оформлено відповідно до Java Code Conventions: назви класів — іменники
у CamelCase, назви методів/змінних — camelCase, константи — UPPER_SNAKE_CASE,
фігурні дужки за K&R-стилем, поля інкапсульовані (private + геттери),
Javadoc-коментарі для класів і ключових методів.
